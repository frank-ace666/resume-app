# 开发流程评估与改进建议

> **评估对象**：简历工坊（Resume Craft）v1.3.1  
> **参考框架**：用户提供的《参考.md》中的 8 阶段软件开发流程  
> **评估日期**：2026-10-18  
> **评估依据**：Git 历史、`docs/` 文档、`package.json`、界面与 PDF 实际验收  
> **说明**：本文是流程评估，不是代码审计。项目为单人、AI 辅助、本地离线的 Windows 桌面应用，因此不套用大型团队的重量级流程。

---

## 一、结论摘要

**总体判断：流程方向是对的，技术实现与交付意识明显强于需求验证与自动化测试。**

这个项目已经具备一个可交付 MVP 的骨架：目标用户明确、核心流程完整、技术设计有文档、版本与更新机制齐全。但它目前更像“一个能力很强的个人项目”，还不是“一个可以持续接收真实用户反馈并稳定迭代的产品流程”。

| 阶段 | 现状 | 评分（1–5） |
|---|---|---|
| 1. 需求分析 | 目标用户与价值主张清楚，但没有需求文档、用户验证和成功指标 | **2** |
| 2. 产品设计 | 主流程完整，异常分支考虑较多；缺 PRD、原型和验收标准 | **3** |
| 3. 技术设计 | 分层清晰、约束文档化、数据迁移有设计；缺 ADR 与自动化约束 | **4.5** |
| 4. 开发实现 | 小步提交、严格 TypeScript、模块边界清楚；缺 lint / test / CI | **4** |
| 5. 软件测试 | 有一次高质量、脚本化的内测；但没有沉淀为可重复测试，最近仍漏掉 PDF 缩放裁切与空白尾页 | **2.5** |
| 6. 部署上线 | 有 NSIS 安装包、GitHub Releases、检查更新；缺签名、校验和、发布清单与 CI | **3** |
| 7. 反馈迭代 | 有应用内反馈、邮件、更新日志；缺 issue 模板、分诊规则和指标闭环 | **2.5** |
| 8. 维护运营 | 有版本与文档；缺依赖更新节奏、安全清单、诊断与备份策略 | **2** |

**综合：3 / 5。** 对个人 MVP 来说合理，对“持续面向更多用户分发”来说还不够。

**一句话建议：下一步不要急着加功能，先把“一次性的人工验证”变成“可重复的自动验证”，再把需求与反馈闭环补上。**

---

## 二、做得好的地方

先明确哪些做法值得保留，避免为了“流程完整”把有效的个人实践改坏。

1. **MVP 边界大体正确**
   核心闭环是“填写 → 预览 → 换模板 → 导出 PDF”，和参考文档建议的第一版四件事高度一致。没有一上来做账号、云端、协作、权限。

2. **技术设计有真正的文档**
   `docs/development-reference.md` 覆盖架构、模板分层、打印色板、PDF 管线、数据版本等，且解释了“为什么这样做”。这在个人项目中很少见。

3. **有版本、更新日志和更新检查**
   `docs/CHANGELOG.md`、`src/data/releases.ts`、应用内检查更新、GitHub Releases 形成了基本的发布闭环。

4. **有测试与复盘意识**
   `docs/beta-test-report.md` 记录了 4 份简历 × 3 模板 × 3 主题色、11 个界面状态、4 次 PDF 导出，并用脚本驱动、解析 PDF 二进制校验页面尺寸。`docs/errors-and-fixes.md` 也记录了踩坑过程。这说明团队知道“能运行 ≠ 可交付”。

5. **隐私与本地优先**
   无后端、无登录、不上传简历；反馈走用户自己的邮件客户端。对简历这种敏感数据，这是正确的产品决策。

6. **最近的用户文档修正**
   README 已从开发者视角改为用户视角，删除了 AI 声明、技术栈、构建命令、项目结构等开发内容。这是“面向用户”的重要一步。

## 三、逐阶段评估

### 1. 需求分析

**现状与证据**

- 产品定位清楚：面向求职新手（学生、转行从业者）的轻量化简历制作桌面应用。
- 功能从 6 步表单、3 套模板，扩展到 7 步、7 套模板、自定义联系方式、检查更新、帮助与反馈。
- 仓库中**没有** `PRD`、需求文档、用户画像、访谈记录、可用性测试记录或成功指标。
- `docs/CHANGELOG.md` 末尾有“优化建议（待评估）”，说明有一个非正式的需求池，但没有准入标准和优先级依据。

**判断**

方向合理，但需求阶段偏薄。当前需求更多来自开发者/ AI 的判断，而不是来自真实用户的验证。参考文档强调：用户提出的功能不一定是最佳方案，开发前要先确认问题真实存在、频率足够高、现有工具确实不足。

**风险**

- 容易功能蔓延：每个“看起来不错”的功能都进入开发，但没有验证它是否解决核心问题。
- 难以判断版本是否成功：没有“首次导出 PDF 成功率”“完成一份简历耗时”“用户卡在哪一步”等指标。
- 面向更多用户后，可能做出用户并不需要的复杂功能。

**改进**

- 写一份一页纸的 `docs/PRD.md`，至少包含：
  - 目标用户与 2–3 个典型场景；
  - 用户要完成的 Job（例如“30 分钟内做出一份可投递的简历”）；
  - 现有工具的不足（模板收费、操作复杂、排版差、不会写项目经历……）；
  - MVP 范围与**明确不做**的功能；
  - 验收标准与成功指标。
- 找 5–10 位目标用户做简短访谈；观察 3 位用户实际做一份简历，记录卡点、耗时和放弃原因。
- 给需求池加一个准入表：问题证据、影响人数/频率、实现成本、是否符合产品目标。四项都过再排期。
- 定义 3–5 个可衡量的指标，例如：首次导出 PDF 完成率、平均完成时间、模板切换次数、导出失败率、7 日内再次打开率（若未来有可选统计）。

### 2. 产品设计

**现状与证据**

- 主流程清晰：个人信息 → 教育 → 工作 → 技能 → 项目 → 自我评价 → 简历检查 → 导出。
- 异常分支考虑较多：自动保存、空状态、字段校验、模板切换保留内容、旧数据补齐、单实例锁、导出前校验闸门。
- `docs/design-benchmark-apple.md` 对界面完成度做了系统对标。
- 但没有独立的产品流程文档、页面原型、交互说明和逐流程验收标准。

**判断**

产品设计“做在代码里”的部分是合格的，甚至优于很多 MVP；但缺少可评审、可测试、可交接的设计产物。对单人项目，这会表现为“只有作者知道完整流程和边界”。

**风险**

- 新功能没有先在流程层面推演，容易在实现后才发现交互冲突。
- 测试无法对照验收标准，容易只验证“页面能打开”，而不是“用户能完成任务”。
- 未来如果请人协作或做用户支持，学习成本高。

**改进**

- 在 PRD 中补一张用户流程图和一张异常矩阵：首次使用、空简历、填到一半退出、无效邮箱、切换模板、打开旧文件、导出失败、超长内容。
- 为每个核心流程写 3–5 条验收标准（Given / When / Then 即可）。
- 新功能先用纸面或 Figma 画 1–2 个关键页面，找 1–2 位目标用户看一遍再写代码。
- 对“填写 → 预览 → 导出”做一次可用性测试，记录完成率、耗时、卡点；这比再加一套模板更能提升产品。

### 3. 技术设计

**现状与证据**

- `docs/development-reference.md` 有 14 章，覆盖架构、数据模型、模板分层、PDF 管线、颜色约束、校验与错误处理。
- 模板与数据模型分离、打印安全色板、`normalizeResumeData` 数据迁移、校验谓词单一来源，这些都是有意识的设计。
- Electron 安全设置包含 `contextIsolation: true`、`nodeIntegration: false`、外链白名单、单实例锁。
- 没有 ADR（架构决策记录），没有 lint 规则自动阻止“模板里使用 Tailwind 调色板类/透明度修饰符”，没有 typecheck / test 脚本。

**判断**

这是全流程中最扎实的一环。技术选型克制（本地优先、无后端），对 PDF 光栅化、oklch/color-mix、中文字距等坑有真实记录。

**风险**

- 文档会漂移：代码改了、文档没改，后续判断会被旧文档误导。
- 关键约束依赖开发者记忆；例如模板颜色约束一旦被新代码破坏，只有导出 PDF 时才会暴露。
- 安全加固尚未完成：`sandbox: false`、`index.html` 没有 CSP；开发环境已出现 Electron 安全警告。

**改进**

- 建 `docs/adr/`，为关键决策各写一页：为什么选 Electron、为什么本地优先、为什么用 html2canvas、为什么模板与数据模型分层、为什么暂不做账号/云同步。
- 把“模板不得使用调色板类/透明度修饰符”变成自动检查：一条测试扫描模板文件，或加 ESLint 规则；不要只靠注释。
- 增加 `typecheck`、`lint`、`test` 脚本，并在提交前/CI 中运行。
- 安全设计清单：CSP、sandbox 可行性评估、IPC 参数校验、依赖审计、外链白名单（已有）。
- 把 PDF 文字不可选中列为明确的产品技术债，评估 `pdfmake` / `pdf-lib` 方案，而不是无限期搁置。

### 4. 开发实现

**现状与证据**

- 20 个提交，提交信息清楚，基本是“一个主题一个提交”。
- 严格 TypeScript；组件、store、utils、types 分层清楚；有 ErrorBoundary、Toast、空状态、确认对话框等基础设施。
- 没有 ESLint / Prettier 配置，没有测试脚本，没有 CI；`package.json` 只有 dev/build/preview/package。
- AI 辅助开发占比高；原 README 有 AI 声明（现已按用户要求删除）。

**判断**

开发执行质量高，Git 习惯好。但“AI 生成代码 + 人工看一眼”不是稳定的质量 gate。参考文档明确指出：AI 生成代码不等于功能实现，功能能运行也不等于达到交付标准。

**风险**

- 回归靠人肉记忆；一次看似无关的重构可能破坏导出、迁移或模板布局。
- 代码风格靠自觉，没有格式化/静态检查兜底。
- 复杂改动（PDF、数据迁移）缺少先写测试或先做 spike 的习惯。

**改进**

- 建立 Definition of Done：代码 + 类型检查 + lint + 测试 + 手工冒烟 + 文档/更新日志。
- 加 `husky` + `lint-staged`（或至少 npm scripts），提交前跑 typecheck/lint/test。
- 即使是单人项目，也用短分支/PR 做一次自审 diff；复杂改动先写测试或 spike。
- 把 AI 当作“实现加速器”，但需求判断、架构决策、验收标准必须由人负责。
- 每次修复 bug 时补一条回归测试（先从最重要的 PDF、数据迁移、校验规则开始）。

### 5. 软件测试

**现状与证据**

- v1.2.0 内测报告质量很高：4 份简历 × 3 模板 × 3 主题色、11 个界面状态、4 次 PDF 导出；脚本驱动真实构建产物；解析 PDF 二进制校验页面尺寸；发现并修复 9 项缺陷。
- 但仓库中没有测试目录、测试框架、测试脚本或 CI；内测报告里的驱动脚本没有沉淀下来。
- 2026-10-18 的验收中仍发现两类测试矩阵未覆盖的问题：
  1. 预览处于「适应宽度」缩放（实测 124%）时，PDF 只截到左上角，右侧日期与文字被裁掉；
  2. 底部留白导致现代模板多出一张只有 57px 白边的空白尾页。
- 单元测试缺失：校验函数、`normalizeResumeData`、日期格式化、联系方式模型、分页计算都没有自动化覆盖。
- 兼容性/安全测试没有系统化记录。

**判断**

测试意识和一次性测试质量都很高，但**可重复性低**。这是当前最大的流程短板。参考文档中“PDF 生成成功但排版被截断，功能仍不算完成”的例子，在项目里真实发生了。

**风险**

- 每次改模板/样式/PDF 管线，都可能悄悄破坏另一个模板或另一种缩放状态。
- 旧数据迁移、导出、校验等高风险逻辑没有回归保护。
- 发布前的验证依赖临时脚本和人工记忆，难以稳定复现。

**改进**

按测试金字塔补一层“薄但关键”的自动化：

| 层级 | 工具建议 | 覆盖内容 |
|---|---|---|
| 单元测试 | Vitest | 邮箱/手机/微信/URL/GitHub/GPA/日期校验；`normalizeResumeData`（旧 level、LinkedIn、微信迁移、未知模板 ID）；`buildContacts` 标签/顺序/去重；日期格式化；分页纯函数 |
| 组件测试 | React Testing Library | 个人信息/技能表单；模板选择器；校验错误展示；空状态 |
| E2E | Playwright `_electron` | 启动真实构建产物 → 注入示例数据 → 切换 7 套模板 → 断言联系方式标签/无技能等级 → 导出 PDF → 校验页数与页面尺寸 |
| 视觉回归 | 截图 + 像素对比 | 7 套模板 × 关键缩放（100% / 适应宽度 / 200%）× 明暗强调色 |
| 异常/数据 | Vitest + E2E | 空简历、半填、超长内容、两页以上、无效 JSON、旧存档、重复联系项、超长 URL、图片 |
| 安全 | 人工 + 工具 | CSP、sandbox、IPC 参数校验、`npm audit`、外链协议白名单 |

同时：

- 把 v1.2.0 的脚本整理进 `tests/`，不要只留在报告里。
- 加 `npm run typecheck`、`npm run lint`、`npm test`、`npm run test:e2e`。
- 加 CI（GitHub Actions，Windows runner）：每次 push/PR 跑 typecheck、lint、单元测试、build；发布前跑 E2E + PDF 冒烟。
- 写 `docs/test-plan.md`：测试矩阵、环境、数据、通过标准；每个用例关联到需求/验收标准。
- 发布前至少覆盖：7 套模板 × 1 份完整简历 × 2 种缩放 × 1 次 PDF 导出；再加 1 份多页简历。

### 6. 部署上线

**现状与证据**

- `electron-builder` 产出 NSIS 安装包与 `win-unpacked` 免安装版。
- 有 GitHub Releases、应用内检查更新、README 安装说明。
- 没有代码签名、SHA256 校验和、CI 发布流程、干净虚拟机安装记录、回滚方案或国内下载镜像。
- README 已提示 Windows「未知发布者」的处理方式。

**判断**

对小范围分发够用；对陌生用户下载安装，信任成本偏高。参考文档强调“自己电脑运行成功 ≠ 用户能正常使用”，部署后还要做实际环境测试。

**风险**

- SmartScreen 警告会显著降低下载/安装转化率。
- 没有校验和，用户无法确认安装包完整性。
- 手工发布容易漏步骤（版本号、更新日志、安装包、更新检查）。
- 国内访问 GitHub 不稳定，下载链路可能中断。

**改进**

- 建立发布清单：
  1. 版本号 + 更新日志 + `releases.ts`；
  2. typecheck / lint / unit / E2E / build；
  3. 在干净 Windows 虚拟机安装、启动、填写、导出 PDF；
  4. 验证检查更新；
  5. 生成 SHA256；
  6. 打 tag、上传 GitHub Releases；
  7. 保留上一版本，准备回滚说明。
- 代码签名（如有条件）或至少提供校验和与信任说明。
- 增加国内可访问的下载页/镜像；在 README 中写清备用获取方式。
- 把发布流程脚本化/CI 化，减少手工步骤。

### 7. 反馈迭代

**现状与证据**

- 应用内有「帮助与反馈」模块，反馈通过用户自己的邮件客户端发送；有 GitHub 仓库和更新日志。
- 没有 issue 模板、反馈分诊规则、用户访谈记录或指标看板。
- 无后端、无遥测，这是隐私上的优点，但也意味着没有自动化的用户行为数据。

**判断**

反馈“入口”有了，但“闭环”没建立：收集之后如何归类、如何判断优先级、如何验证改进是否有效，目前没有固定做法。参考文档强调：不是每条建议都直接变成开发任务，要看频率、影响、成本和产品目标。

**风险**

- 功能优先级依赖直觉，容易出现“做了很多，但没解决最痛的问题”。
- 用户反馈散落在邮件/对话中，无法追踪是否已解决。
- 无法判断版本是否真的改善了体验。

**改进**

- 建 GitHub Issue 模板（Bug / 功能建议 / 使用问题）和标签（P0/P1/P2、频率、影响范围、模块）。
- 做一张简单的反馈分诊表：问题、证据、影响人数、频率、成本、是否符合目标、决定（做/不做/以后做）。
- 每月复盘一次反馈，选 1–3 个高影响问题进入下个迭代；把决定和理由写进 CHANGELOG 或 roadmap。
- 在应用内反馈中自动附带（经用户同意）版本号、系统版本、当前模板、可选诊断信息，降低沟通成本。
- 没有遥测时，用 5–10 位用户的可用性测试 + 反馈计数代替；不要为了指标引入侵入式统计。

### 8. 维护运营

**现状与证据**

- 有版本号、更新日志、检查更新、开发文档、错误记录。
- 依赖使用 `^` 范围；没有 Dependabot/Renovate、CI、`npm audit` 流程或安全审查清单。
- 安全配置部分到位，但 `sandbox: false`、无 CSP；安装包未签名。
- 用户数据主要依赖 localStorage + 手动 JSON 导出；没有自动备份/恢复策略、崩溃日志或诊断导出。
- 没有性能预算（启动时间、PDF 导出时间、包体积）或兼容性测试节奏。

**判断**

基本维护意识有，但缺少节奏与自动化。随着用户增多，依赖升级、安全漏洞、数据丢失和系统兼容会成为主要风险。

**改进**

- 每月维护窗口：依赖升级、`npm audit`、Electron/Windows 兼容性检查；安全补丁随时处理。
- 安全清单：CSP、sandbox 评估、IPC 输入校验、外链白名单（已有）、依赖审计、发布签名。
- 数据安全：增加自动备份/轮转备份或定期提醒导出 JSON；提供恢复说明。
- 诊断能力：本地日志 + 「导出诊断信息」按钮；可选、隐私友好的崩溃/错误上报。
- 性能预算：启动时间、首次导出 PDF 时间、安装包体积；每次发布记录一次。
- 文档保鲜：每次发布检查 README、PRD、测试计划、CHANGELOG 是否同步。

## 四、流程层面的总体判断

### 4.1 已经符合参考文档的部分

- **从问题出发**：产品不是“为了用技术而用技术”，Electron + 本地优先是合理选择。
- **MVP 思路**：先做填写、预览、模板、PDF，没有过早引入账号和云端。
- **迭代而非瀑布**：提交历史显示功能、修复、文档交替推进，符合参考文档“真实项目不是严格瀑布”的判断。
- **技术设计与文档**：这一项明显高于个人项目平均水平。
- **测试与复盘意识**：内测报告、错误记录、设计对标都说明作者在认真验证，而不是“写完就发”。

### 4.2 与参考文档的主要差距

1. **需求没有文档化、没有用户验证**：有定位，但没有需求文档、访谈、成功指标。
2. **测试没有制度化**：一次性的脚本化内测很优秀，但没有变成仓库里的自动化测试和 CI。
3. **发布没有清单化**：能打包、能发布，但缺少签名、校验和、干净环境验证与回滚方案。
4. **反馈没有闭环**：有入口，但没有分诊、优先级和效果验证。
5. **维护没有节奏**：没有依赖更新、安全审计、备份/诊断的固定动作。

### 4.3 关于 AI 辅助开发

参考文档对 AI 的判断同样适用于本项目：

> AI 生成了代码，不等于功能已经实现；功能能够运行，也不等于软件已经达到交付标准。

这个项目的优势是把 AI 用在“实现和文档”上，同时保留了大量人工验收；风险是验收仍以临时脚本和人工走查为主。**AI 不是流程问题，验证不足才是。** 把验证自动化，AI 的收益才会稳定放大。

## 五、建议的轻量流程（适合个人 / 小团队）

不需要引入大型团队的重量级流程。建议把参考文档的 8 阶段压缩成下面这个循环，每个迭代（1–2 周）走一遍：

```
1. 需求准入（半天）
   └─ 一页纸：问题、用户、证据、范围、不做什么、验收标准、指标

2. 产品设计（半天–1 天）
   └─ 主流程 + 异常矩阵 + 关键页面草图

3. 技术设计（半天）
   └─ 涉及模块、数据迁移、风险、测试计划

4. 实现（1–3 天）
   └─ 小步提交；逻辑与测试一起写

5. 验证（半天）
   └─ typecheck / lint / unit / E2E / 视觉对比 / 手工冒烟

6. 发布（半天）
   └─ 发布清单：版本、日志、构建、安装、PDF、校验和、上传

7. 复盘（半小时）
   └─ 反馈分诊 + 指标 + 下个迭代选一个最重要的问题
```

**固定节奏**

- 每周：30 分钟自查（进度、风险、未解决问题）。
- 每月：依赖更新 + 安全审计 + 反馈复盘。
- 每季度：3–5 位目标用户访谈或可用性测试。

**建议产出的文档**

| 文档 | 作用 | 频率 |
|---|---|---|
| `docs/PRD.md` | 目标用户、问题、范围、验收标准、指标 | 每季度/大版本 |
| `docs/test-plan.md` | 测试矩阵、环境、数据、通过标准 | 每次大功能 |
| `docs/release-checklist.md` | 发布前逐项检查 | 每次发布 |
| `docs/adr/` | 关键技术决策及理由 | 重大决策时 |
| `docs/feedback-triage.md` | 反馈归类、优先级、决定 | 每月 |
| `docs/CHANGELOG.md` | 版本变更 | 每次发布（已有） |

**Definition of Done（建议）**

- [ ] 对应需求/验收标准已写明
- [ ] 正常路径 + 至少 2 个异常路径已验证
- [ ] 新增/修改逻辑有单元测试或 E2E
- [ ] `typecheck` / `lint` / `test` 通过
- [ ] 7 套模板与 PDF 导出冒烟通过（如涉及模板/渲染）
- [ ] 旧数据迁移验证通过（如涉及数据结构）
- [ ] README / CHANGELOG / 相关文档已更新
- [ ] 版本号与发布说明已准备

## 七、结论

**流程合理吗？**

- 对“单人 + AI 辅助 + 本地桌面 MVP”来说，**合理且高于平均水平**：目标清楚、技术设计扎实、有版本与发布、有一次高质量内测。
- 对“持续面向更多用户分发、长期维护”来说，**还不够**：需求验证、自动化测试、发布信任、反馈闭环、维护节奏都还依赖个人记忆和一次性工作。

**最值得保留的**

- 小步提交与清晰的提交信息；
- 技术设计文档与 PDF/数据迁移的边界意识；
- 内测报告、错误记录、设计对标的复盘文化；
- 本地优先与隐私友好的产品决策；
- 面向用户的 README（已修正）。

**最需要补的**

1. **需求验证**：PRD + 5–10 位用户访谈/可用性测试 + 成功指标。
2. **自动化回归**：Vitest + Playwright/Electron + 视觉对比 + CI。
3. **发布与维护清单**：签名/校验和、干净环境验证、依赖/安全/备份节奏。

**不要做的**

- 不要为了“流程完整”引入重型审批、复杂看板或大规模文档；
- 不要在缺少用户证据时继续堆功能；
- 不要把“AI 写完了”当成“功能完成了”。
