# 对标 Apple / macOS 系统应用的优化建议

> 编写日期：2026-10-10 · 对标版本：v1.2.0
> 目的：以 Apple 官方 HIG 与其系统应用（Finder / Mail / Notes / Pages / 系统设置）为参照，
> 找出本项目在「桌面应用完成度」上的真实差距，并给出可执行的改进路线

---

## 一、怎么读这份文档

对标 Apple 有一个必须先讲清的前提：**本项目是 Windows 优先的桌面应用，不是 macOS 应用。**
照搬 macOS 约定（无保存按钮的文档模型、菜单栏必需、交通灯按钮、毛玻璃材质）在 Windows 上反而是错的。

所以本文把所有差异分成三类，每类结论不同：

| 类别 | 含义 | 处理方式 |
|---|---|---|
| **A. 可迁移的设计品质** | 与平台无关的工艺水准：排版尺度、语义色层级、动效纪律、空间一致性、可达性 | **应当采纳** |
| **B. 平台专属约定** | macOS 独有约定（菜单栏、⌘ 快捷键、无保存模型、vibrancy） | 取其**意图**，用 Windows 的对应物实现 |
| **C. 不该照搬的** | 与既定产品决策冲突，或中文字形不适用的 | **明确不做**，并说明理由 |

调研来源以 Apple HIG、Apple 开发者文档、WWDC 议题为主。**采集过程有一个限制**：调研工具对所有域名（含 developer.apple.com）均被网络策略拦截，内容取自检索摘要对原文的转述。文中对每条结论标注了可信度：

- `[HIG]` Apple 官方 HIG / 开发者文档原文
- `[系统应用]` Apple 已发布应用的可观察行为或 API 语义
- `[社区实测]` 第三方测量或评论，未经 Apple 确认

## 二、结论摘要

| # | 差距 | 类别 | 优先级 | 现状 |
|---|---|---|---|---|
| 1 | **完全没有键盘快捷键** | A | **P0** | 实测 Ctrl+S/N/O/Z/P 全部无响应 |
| 2 | **不记忆窗口位置与尺寸** | A | **P0** | 主进程固定 1280×800，无状态持久化 |
| 3 | 正文色用固定灰值，非带 alpha 的语义层级 | A | P1 | `ink/ink-2/ink-3` 为实色 hex |
| 4 | 不提供「跟随系统强调色」 | A | P1 | 只有 8 个预设 + 自定义 |
| 5 | 动效加在**高频**交互上 | A | P1 | 分区切换每次都播 300ms 动画 |
| 6 | 面板收展未用弹簧参数 | A | P2 | 目前是 300ms cubic-bezier |

| 8 | 无拖放入口 / 无文件关联 / 无最近文件 | B | P2 | 只能通过「打开」对话框 |
| — | 键盘焦点可见性 | A | ✅ 已达标 | 实测 22 个 Tab 停靠点全部有可见指示 |
| — | 减少动态效果 | A | ✅ 已达标 | 实测动画/过渡时长降为 ~0 |

## 三、逐项分析

### 3.1 排版 `[HIG]`

Apple 的 macOS 文本样式表（官方）：

| 样式 | 字重 | 字号 | 行高 |
|---|---|---|---|
| Large Title | Regular | 26 | 32 |
| Title 1 | Regular | 22 | 26 |
| Title 2 | Regular | 17 | 22 |
| Title 3 | Regular | 15 | 20 |
| Headline | **Bold** | 13 | 16 |
| **Body** | Regular | **13** | 16 |
| Callout | Regular | 12 | 15 |
| Subheadline | Regular | 11 | 14 |
| Footnote / Caption | Regular | 10 | 13 |

**对照本项目**：界面主字号用了 13px，与 macOS Body 的 13pt 一致 —— 这一条已经对齐。差异在**层级数量**：Apple 有 11 级，本项目实际只用了 15 / 14 / 13 / 12 / 11 / 10 六级，缺少 17pt（Title 2）这一档，导致「页面标题」与「卡片标题」区分度不足。

**但行高不能照搬。** Apple 的 Body 行高比是 16/13 ≈ **1.23**，那是为 SF Pro 拉丁字形设计的。中文需要更大行距，这不是审美偏好而是可读性要求。本项目正文用 13px / 行高 1.55，是合理的。

> `[社区实测]` Apple 并未发布中文断行规则，其依赖 Core Text 约定。中文标点避头尾、`——`/`……` 不可跨行等规则来自 W3C clreq 与 GB/T 15834，**不要**去 HIG 里找。

**建议**：补一个 17px 的标题档位用于面板标题；行高维持现状，**明确记录「不采用 1.23」是因为中文字形**，避免后来者误改。

---

### 3.2 颜色与语义色 `[HIG]` `[社区实测]`

Apple 的文本色不是固定灰值，而是**带 alpha 的层级**（社区在 macOS 上实测的数值）：

| 语义色 | 浅色模式 | 深色模式 |
|---|---|---|
| `labelColor` | rgba(0,0,0, **0.847**) | rgba(255,255,255, 0.847) |
| `secondaryLabelColor` | rgba(0,0,0, **0.498**) | rgba(255,255,255, 0.549) |
| `tertiaryLabelColor` | rgba(0,0,0, **0.247**) | rgba(255,255,255, 0.247) |
| `quaternaryLabelColor` | rgba(0,0,0, **0.098**) | rgba(255,255,255, 0.098) |

用 alpha 而不是固定灰，好处是**文字自动适配其所在表面**：同一层级文案放在白色卡片、浅蓝底、灰色 hover 背景上都保持一致的视觉权重。固定灰值在有色背景上会偏轻或偏重。

本项目现在的 `--color-ink / ink-2 / ink-3` 是 `#202124 / #5f6368 / #80868b` 实色。放在 `bg-hover`（`#f1f3f4`）与 `bg-brand-soft`（浅蓝）上时权重会漂移。

**建议**（P1）：把文字色令牌改为 alpha 版本，例如 `--color-ink: rgb(0 0 0 / 0.87)`、`--color-ink-2: rgb(0 0 0 / 0.5)`、`--color-ink-3: rgb(0 0 0 / 0.28)`。深色模式日后直接用白色同 alpha 即可，省一套色板。

> ⚠️ 注意：`quaternaryLabelColor` 一档 Apple 明确限定只用于**大号次要文字、分隔线、大图标**，不可用于正文，也不可放在 thin/ultraThin 材质上。本项目如果加这一档要遵守。

另外 Apple 的 HIG 明确要求：**不得仅用颜色传达含义**（其系统设置里有「不必依赖颜色区分」开关）。本项目做得好 —— 严重程度徽标、导航完成态、主题色选中态都同时用了图标、对勾或形状，不是只靠颜色。

### 3.3 动效 `[HIG]` `[系统应用]`

Apple 的动效原则（HIG 原文要点）：

- 动效要有**目的**，不要盖过内容
- 动效必须**可选**（可关闭）
- 追求**跟随手势的真实反馈**，而非装饰
- **简洁精确**
- **避免在频繁发生的交互上加动效**
- **让人能取消动效**

弹簧参数（WWDC23「Animate with springs」给出的具体值）：

| 场景 | damping | response |
|---|---|---|
| 移动 / 重定位 | 1.0 | 0.4s |
| 旋转 | 0.8 | 0.4s |
| **抽屉 / 面板** | **0.8** | **0.3s** |

两条空间一致性规则：**进出走同一条路径**；**可逆过渡的缓动要镜像**。以及**中断时从当前呈现值出发、携带速度重新定向**，不能"撞墙"。

**对照本项目**：`prefers-reduced-motion` 已实测生效（动画 0.3s → 1e-06s，过渡 0.12s → 1e-06s），「动效可选」这条达标 ✅。

真正的问题是**第 5 条**：分区切换的 `anim-fade-slide-in`（300ms 淡入 + 位移）**每次切换分区都播**。按 Apple 的标准，切换分区属于高频交互，不该加动画。同理，新增条目时每个 `EntryCard` 都播 `anim-pop-in`（200ms），连续添加数条会显得吵。

**建议**（P1）：
- 分区切换：降为**纯淡入 150ms**，或直接去掉位移分量；不要 300ms + 位移
- 列表项入场：去掉逐个 `anim-pop-in`，或只在首次渲染时播
- 面板收展（编辑器折叠 / 导航折叠）：改用弹簧近似，`damping 0.8 / response 0.3` 对应的视觉感受，CSS 侧可用 `cubic-bezier(0.32, 0.72, 0, 1)` 近似

### 3.4 控件与交互 `[HIG]` `[系统应用]`

- **默认按钮与键盘焦点是两个概念**：macOS 上 Return 触发「默认按钮」，Space 触发「当前聚焦控件」。本项目在 Web 环境，这条不直接适用，但**提醒不要给所有按钮都加回车触发**（表单里会误提交）。
- **hover 不能是唯一的可点击信号**：HIG 明确「若元素可点击，它必须**在无 hover 时也看起来可点击**」，且「不要用 hover 来发起动作」。本项目模板缩略图有常驻边框与选中态 ✅；但技能快捷添加芯片（`SkillsForm`）只有 hover 变色，静息态是浅色描边，可点击性偏弱。
- **无效输入的就地提示**：`[社区实测]` 未取得 HIG 原文，通行做法是**失焦时校验**（不是每次按键），错误提示紧贴字段而非浮动 toast。本项目目前无表单校验，字段错误只能靠「简历检查」事后发现。

**建议**（P2）：给技能芯片等"轻量可点击"元素补一个常驻的次要按钮外观；表单校验列入后续（当前靠检查模块兜底是合理的产品取舍）。

---

### 3.5 窗口与布局 `[HIG]` `[系统应用]`

Apple 的三段式职责划分是一句很好用的判据：

> **侧边栏 = 顶层导航；工具栏 = 当前屏幕的动作；检查器 = 当前选中的细节。**

本项目结构与之吻合：`NavDrawer` 是顶层导航，`AppBar` 放全局文件动作，`PreviewToolbar` 放预览动作 ✅。

侧边栏宽度：`[社区实测]` macOS 侧边栏 220–280px。本项目展开态 248px、折叠态 72px，落在区间内 ✅。（折叠图标栏的准确宽度**未找到权威数字**，Apple 各应用不一致，需真机测量。）

**但 HIG 有一条本项目未满足**：

> 侧边栏**避免在底部放关键信息或操作**。

本项目的 `NavDrawer` 底部放了「填写进度」进度条。它是信息而非操作，风险较低，但按 HIG 应移到内容区或状态栏。**建议**（P2）：进度信息下沉到 `StatusBar`，侧栏底部留空。

**窗口状态记忆**（P0）：Apple 应用通过 frame autosave + state restoration 记住窗口位置、尺寸、滚动位置与选中项，重启后原样恢复。本项目主进程写死 1280×800，每次启动都回到默认位置。Electron 侧实现简单（保存 `getBounds()` 到文件，启动时 `setBounds()`），且 Windows 用户同样期待这个行为。

---

### 3.6 键盘与可达性 `[HIG]` ⚠️ **本项目最大缺口**

Apple 把「命令必须可从菜单栏到达」写成了强要求，理由是三条：可被找到、可分配快捷键、**可被全键盘访问的用户使用**。

> 原文要点：即使命令在应用别处也能触达，也应当在菜单栏列出；**把命令排除在菜单栏之外 —— 即使是很少用或高级的命令 —— 会有让所有人都难以找到它们的风险。**

**实测结果（本项目）**：

| 组合键 | 应用是否响应 |
|---|---|
| Ctrl+S（保存） | ❌ 无响应 |
| Ctrl+N（新建） | ❌ 无响应 |
| Ctrl+O（打开） | ❌ 无响应 |
| Ctrl+Z（撤销） | ❌ 无响应 |
| Ctrl+P（打印/导出） | ❌ 无响应 |

**全部为空。** 应用没有任何键盘加速键，也没有 Electron 应用菜单 —— 意味着 7 个分区的切换、导出、保存全都要靠鼠标点。

这不只是 macOS 问题：Windows 用户同样习惯 Ctrl+N / Ctrl+O / Ctrl+S，这是跨平台的桌面软件基本预期。

**焦点可见性已达标** ✅：用真实键盘 Tab 遍历 22 个停靠点，**全部有可见焦点指示**（无指示为 0）。这一项不需要改。

**建议**（P0）：
1. 用 Electron `Menu.setApplicationMenu` 建立应用菜单，把现有命令全部列入（Windows 上还能顺带获得 Alt 键导航）
2. 补标准加速键：`Ctrl+N` 新建、`Ctrl+O` 打开、`Ctrl+S` 保存、`Ctrl+Shift+S` 另存、`Ctrl+E` 导出 PDF、`Ctrl+Z / Ctrl+Shift+Z` 撤销重做（需先接 zundo）、`Ctrl+= / Ctrl+-` 预览缩放、`Ctrl+0` 重置缩放
3. 补分区跳转：`Ctrl+1…7` 直达七个分区
4. 格式检查：菜单项末尾的「…」只在需要后续输入时才加（如「导出 PDF…」），「关于」「退出」不加

### 3.7 系统集成 `[系统应用]`

Apple 应用在系统层面还有一批集成点。**平台专属的部分不做**，但其**意图**在 Windows 上有对应物：

| macOS 能力 | 意图 | Windows 对应物 | 建议 |
|---|---|---|---|
| 拖拽到 Dock / Finder 拖出 | 缩短文件路径 | 拖入窗口打开、拖出到资源管理器 | P2 可做 |
| 文件关联（`CFBundleDocumentTypes`） | 双击 `.json` 直接用本应用打开 | 注册文件关联 | P2 可做 |
| 最近打开（Dock 菜单） | 快速回到最近文档 | 跳转列表（Jump List） | P2 |
| 全屏隐藏交通灯后布局自适应 | 布局需容忍控件消失 | — | 不适用 |
| 滚动条随输入设备自动切换 overlay | 触控板淡出、鼠标常驻 | Windows 惯例是常驻滚动条 | **不做**（见下节） |

## 四、明确**不**建议照搬的部分

这一节同样重要 —— 盲目对标会让产品失去已有的正确决策。

### 4.1 不引入 macOS 的「无保存按钮」文档模型

Apple 的 `NSDocument` 自动保存模型下，文档持续自动落盘、没有用户可见的保存步骤。但：

- 本应用的产品模型是 **JSON 文件 + 本地自动保存** 的混合体，用户心智里「另存为一份文件发出去」是核心动作（导出 PDF、保存 JSON）
- 本项目**已经**有 2 秒防抖的 localStorage 自动保存，只是同时保留了显式保存 —— 这是正确的折中
- 去掉显式保存按钮会让「我的文件在哪」变得不明确

**结论：保留显式保存。** 可在细节上向 Apple 靠拢 —— 用标题栏的「已修改」圆点传达未保存状态（本项目状态栏已有等价信息）。

### 4.2 不采用 Apple 的「尽量减少投影」原则

HIG 的 Deference 原则原文点名要**尽量减少边框、渐变与投影**，让内容优先。这与本项目**明确选择的 Material 风格**直接冲突。

理由：
- 用户明确要求 Gmail / YouTube 式风格，而 Material 用 elevation 表达层级是核心手段（Material 把阴影当作表面分离的**唯一**视觉线索，与 Apple 立场相反）
- Apple 自己的方向也在变：2025 年起的 Liquid Glass 体系把「材质层」重新引回控件与导航层

**结论：保留 Material elevation。** 但采纳其**精神**：本项目已做到「大量卡片同屏时用描边而非阴影」（见 `Card.tsx` 注释），这正是 Deference 想要的效果。

### 4.3 不采用 macOS 的紧行高

见 3.1。Apple 的 1.23 行高比是为拉丁字形设计的；中文需要更大行距。本项目 1.55 不改为 1.23。

### 4.4 不给简历模板引入任何 Apple 风格

第 3.1–3.7 的建议**全部只适用于应用外壳**。简历模板是要打印并过 ATS 解析的文档，其排版约束（单一强调色、纯文字熟练度、无图标、显式 sRGB 色）另有依据，见[开发参考 · 第九节](./development-reference.md)。

若把 macOS 的语义色 alpha 层级搬到模板里，会导致 html2canvas 遇到半透明叠加、且灰度打印结果不可预期。

### 4.5 不引入毛玻璃 / 亚克力材质

Windows 对应的 Acrylic / Mica 在 Electron 中实现受限，且会：

- 破坏预览区截图的确定性（半透明会叠加桌面内容）
- 与「导出 PDF 必须所见即所得」的核心诉求冲突

**结论：不做。**

## 五、建议路线

### P0 — 桌面应用基本预期，建议尽快补

1. **建立应用菜单 + 标准键盘加速键**（3.6）
   - 改动集中在主进程 `electron/main/index.ts`，通过 IPC 把菜单命令转发到渲染进程复用现有 `App.tsx` 回调
   - 这是本报告唯一一项「不做就称不上完整桌面应用」的缺口
2. **记忆窗口位置与尺寸**（3.5）
   - 主进程保存 `getBounds()`，启动时恢复；顺带恢复最大化状态

### P1 — 品质提升

3. 文字色令牌改为 alpha 语义层级（3.2）
4. 主题色增加「跟随系统」选项（Electron 在 Windows 可用 `systemPreferences.getAccentColor()`）
5. 削减高频动效：分区切换降为短淡入、去掉列表项逐个入场动画（3.3）
6. 补 17px 标题档位（3.1）

### P2 — 打磨

7. 面板收展改用弹簧近似曲线（3.3）
8. 嵌套圆角遵循同心关系（父半径 − 内边距）
9. 侧栏底部的进度信息下沉到状态栏（3.5）
10. 拖入文件打开、拖出导出；注册文件关联与跳转列表（3.7）

## 六、调研的不确定性（使用本文档时请注意）

以下几点**未获得权威数字**，落到实现前应真机核实：

| 项 | 状态 |
|---|---|
| macOS 工具栏完整高度（常引 52pt） | 未证实；仅**标题栏 28pt** 有代码佐证 |
| 常规 / 大号按钮高度 | 仅 mini 16pt、small 20pt 有测量值 |
| 侧栏折叠图标栏宽度 | **未找到任何权威数字**，需直接测量 Finder / Mail |
| 中文断行与标点规则 | 来自 W3C clreq / GB/T 15834，**不是** HIG；Apple 无对应公开规范 |
| 表单就地校验细节 | 未取得 HIG 原文 |
| 交通灯按钮尺寸与间距 | 来自社区测量（直径 ~15px、间距 ~24px），非官方 |

另需注意：`[社区实测]` 有可信度较高的报告指出，**Apple 自家应用在 Liquid Glass 之后也未完全遵守 Reduce Motion**。本项目该功能实测生效，在这一项上**已优于对标对象**，不必因对标而降低标准。
